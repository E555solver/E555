3The puzzle

Eternity II has 256 square pieces on a 16 × 16 board. A board is a solution when all 480 junctions are matches and each outward face shows the frame colour.

Nobody has published a solution. The best public boards have a score of 470. The best board in the repository is data/best_465.csv, with a score of 465.

ColourFunction
0Frame colour. It is on each outward face.
1–5Frame-interface colours. They are between two adjacent border pieces.
6–22The 17 inner colours. They are on inner pieces and on the inward face of border pieces.

The piece set has 4 corner pieces, 56 edge pieces and 196 inner pieces. The seed file X1 Piece setFig 1 gives the 4 colours of each piece in this order: top, right, bottom, left.

Side d of a placed piece shows seed side (d + s) mod 4. Here s is the spin. Side 0 is the top, 1 the right, 2 the bottom and 3 the left.

Five clue pieces have known cells. The centre clue is piece 138 at row 7, column 7. E555 does not know which side of its border is the real row 0. Thus it tests the clues at all four orientations.

E555 has three stages (Figure 2):

  1. Stage A puts the 60 border pieces on the four sides.
  2. Stage B grows boards upward, one complete row at a time, to a stop row. Then it fills the other cells with dives.
  3. Stage C takes the best boards. It decreases the number of breaks in their top rows.

Stage B does not try all configurations. Most configurations stop after a few rows. Thus Stage B tries many configurations at low cost and keeps the boards that continue. Stage C uses much time on few boards.

5Containers

Figure 2 shows the inside of S1 E555 pipelineFig 1. A C4 container is a unit that runs or stores data. In E555, each container is a command-line tool, a script set or a data file.

5.1Run scripts

C0 Run scriptsFig 2 holds the scripts in pipeline/ (long, unattended runs) and examples/ (one script for each tool). Each script starts with a block of settings. Change a setting with a NAME=value argument, not with an environment variable.

Each tool writes the file outputs.txt. The next tool reads its input from that file. Each script passes --print_cmd. Thus the log records each exact command.

5.2Stage A: the border

A1 Edge annealerFig 2 puts the 56 edge pieces on the four sides, 14 on each side. It puts the 4 corner pieces on the 4 corners.

A1 models each side as a directed graph. The nodes are the frame-interface colours 1 to 5. Each edge piece is one arc. A legal order of the pieces on a side is an Euler trail of that graph. The BEST theorem gives the exact number of trails:

#trails = t_w(G) × ∏_v (outdeg(v) − 1)!

Here t_w(G) is the number of arborescences of the graph. A1 calculates it with integer Bareiss elimination.

A1 uses simulated annealing with a tabu list. A move swaps edge pieces between sides. The default objective is the sum of log(number of trails) over the four sides. A side with more trails gives Stage B more configurations.

Hard constraints keep each border feasible: the degree balance on each side, a connected graph, and enough inner pieces for the inward colours of the border.

A1 writes D1 rotations.csvFig 2. Each row of D1 is one border: the spins of the 60 border pieces. The beamer flag --random_edges replaces Stage A. The beamer then samples borders itself.

5.3Stage B: growth

  • B1 BeamerFig 2 grows boards from row 1 to the stop row. Then it dives them. Section 6 explains it.
  • B2 FinalizerFig 2 locks the rows at and below a row N. It grows the rows above again. Section 7.1.
  • B3 RoundhouseFig 2 turns the board and refills strips W columns wide with an exact search. Section 7.2.
  • D2 Chain databaseFig 2 holds all legal 5-piece row chains. Only B1 reads it. B2 and B3 build smaller databases of their own.

5.4Stage C: closing

  • C1 DistillerFig 2 screens a large set of boards. It keeps the N best boards.
  • C2 DiverFig 2 runs the end-dive engine on any board file.
  • C3 BacktrackerFig 2 runs greedy dives or an exact depth-first search.
  • C4 EnderFig 2 solves regions of a complete board exactly. It never returns a worse board.
  • C5 TopperFig 2 minimizes the breaks in a band of open cells.

Section 8 explains Stage C.

5.5The board CSV file

One CSV dialect connects all tools. This is D3 Board CSV filesFig 2. Each tool reads the output of the other tools, and its own output.

config_id, score, pos[0..255], rot[0..255]      (514 fields)
  • pos[p] is the cell of piece p. The value 999 means "not placed".
  • rot[p] is the spin of piece p.
  • A reader uses the last 512 fields as pos and rot. It treats all fields before them as metadata.
  • A line that starts with # or % is a comment.

T1 Board toolsFig 2 read board files. The viewer prints the board and marks each break with #. The rank tool sorts boards, for example by breaks, clean rows or clues. The rotate tool turns boards by quarter-turns.

NOTE

tools/E555_rank.py --out F --rescore writes any board file again in the canonical form, with the score in field 2.

6.1The 5-5-5 row decomposition

Each row above row 0 has 16 cells. Column 0 holds a left edge piece. Columns 1 to 15 are three segments:

  • Segment A: columns 1–5, 5 inner pieces.
  • Segment B: columns 6–10, 5 inner pieces.
  • Segment C: columns 11–14, 4 inner pieces, and the right edge piece in column 15.

The key of a segment has 6 colours: the colour on its left side, and the 5 top colours of the row below. Segment A takes its left colour from the left edge piece. Segment B takes it from segment A. Segment C takes it from segment B.

Inner colours (6–22) and frame-interface colours (1–5) do not overlap. A key with a frame-interface colour in its last position can only be segment C. Thus one database serves all three segments.

6.2The chain database

K4 Chain indexFig 3 holds DB[left][b1][b2][b3][b4][b5]. This is a direct-indexed array. For each key, it lists all legal 5-piece chains.

  • The real piece set has 3.12 × 10⁹ chains. D2 Chain databaseFig 2 is 6.4 GB, about 2 bytes for each chain.
  • A chain stores each piece as a 3-bit index into a bucket of the oriented-piece catalog. A bucket holds the piece spins with one (left, bottom) colour pair: 7 at most.
  • K4 sorts the chains of each key by promise: the fan-out of their top colours.
  • The fan-out table fanout[b1..b5] (15 MB) gives the number of chains for a set of 5 top colours, over all 17 left colours. One lookup tells how easily a board can continue.
  • --db_file caches the inner part on disk. Later runs map it read-only. The edge part (about 0.2 GB) depends on the border. K4 builds it again for each border row.
CAUTION

A cache records the clue pieces that it excludes. A run with different clue flags builds the database again. Keep one --db_file for each clue setting.

6.3Configurations

K1 Sweep driverFig 3 reads one border row from D1 rotations.csvFig 2. It lists the orders of the bottom row and of the left column as Euler trails. For each border row, it runs --top_bottoms bottom rows. For each bottom row, it runs --top_columns left columns. The best-ranked are first.

  • Bottom rank. The sum of the log fan-out of the three segments that the bottom row shows.
  • Column rank. K1 turns the column 90°. The column is then a row for vertical chains. K1 counts its 5-cell windows in the same database. It also counts the exact number of segment-A chains for row 1. A column with 0 such chains cannot complete row 1. K1 does not run it.
  • Sampling. --tau_bottoms T and --tau_columns T sample with probability proportional to exp(rank / T), instead of the strict order.

6.4The beam loop

K3 Beam loopFig 3 keeps up to --beam_width K boards for each configuration. It moves the beam up one complete row in each step. Figure 5 shows the calls in one step. Each step has five parts:

  1. Expand. K3 fills segments A, B and C of the next row with chains from K4 Chain indexFig 3. A 256-bit mask records the used pieces, so that each piece is used once. A first pass reads the chains in promise order. A second pass reads the other chains in a random full cycle. Thus K3 does not try a chain twice for one parent.
  2. Test. K9 Parity testFig 3 rejects a child that the colour supply cannot complete (Section 6.6).
  3. Score. K8 ScorerFig 3 gives each child a score (Section 6.5).
  4. Select. K3 removes children with the same frontier signature and keeps the best copy. The signature is a 64-bit hash of the used pieces, the top colours and the clue orientation. These values set the whole future of a board. Then K3 cuts the pool to the beam width. It keeps a score band, with at most --parent_cap children for each parent, and a random band of --frac_rand (default 10 %).
  5. Store. K3 writes each move to an ancestry log. A beam entry uses 128 bytes. K3 builds the output boards again from the log.

The beam width grows late: K × E/2 at row R − 1, and K × E from row R. Here E is --beam_expand (default 4) and R is --beam_expand_row (default 7).

A configuration is extinct when the pool is empty. This is not a proof that no board exists, because the quotas and the cut limit the search.

6.5Scoring

K8 ScorerFig 3 gives each child a score. The score is a sum of terms in nats (units of the natural logarithm). A higher score is better.

Lookahead
log n(A′) + log(1 + f_B′) + log(1 + f_C′)

n(A′) is the exact number of chains for segment A of the next row. f_B′ and f_C′ are the fan-outs of the next B and C windows. When n(A′) = 0, the child cannot complete the next row. K8 then rejects the child.

Closure (--lambda_J, default 1.0)

S_c is the number of free faces of inner colour c. Each free face must meet a face of the same colour. Of all the pairings of the 2A free faces, this fraction matches all colours:

P = ∏_c (S_c − 1)!! / (2A − 1)!!

log P is approximately −A × H(π), with π_c = S_c / 2A. The term rewards colour mixes that concentrate on few colours. A second part of the term penalizes demand for colours in short supply.

Mahalanobis (--lambda_Mahalanobis, default 1.0)

x is the 17-vector of the inner-colour faces on the n placed inner pieces. For a random sample of n of the 196 inner pieces, x has a known mean and covariance. The term is the normalized distance of x from that mean. K8 standardizes it with the children of the previous row. A positive weight rewards colour use that is not typical.

NOTE

The closure term and the Mahalanobis term correlate at about 0.88. To test one term alone, set the weight of the other term to 0.

6.6Colour parity

For each inner colour c, K9 Parity testFig 3 calculates S_c = total_c − consumed_c − required_c. "Required" counts the open top faces and each face that the border will need later. S_c ≥ 0 is a necessary condition. K9 tests it for each child of the beam and for each completed row of the exact search.

The test seldom cuts: 634 cuts in 339 million search nodes. Most of the pruning comes from piece fit.

6.7Exact search to the stop row

After row 6 or 7, the beam keeps only a small part of the legal boards. An exact search from those boards costs little, because its tree dies within a few rows. With --backtrack_row N:

  1. Rows 1 to N − 1 are normal beam rows.
  2. Row N is a beam row. Its best boards are the roots (default: 2 × beam width).
  3. K5 Exact row searchFig 3 searches rows N + 1 to the stop row from each root. It is exact. It goes cell by cell, in row-major order.

The cell rules are:

  • Column 0 is the fixed left column.
  • Columns 1–14 take each unused inner piece spin that fits the left and bottom colours.
  • Column 15 takes each unused right edge piece of the border pool.

A path ends when a cell has no fitting piece, or when a completed row fails the K9 Parity testFig 3 test. The right edge piece must fit at the end of each row. This constraint stops most paths early. K5 writes each board that completes the stop row.

6.8Column-major extension

K6 Column-major extensionFig 3 continues each stop-row board before the dives. It is a second exact search with no breaks. It covers rows S + 1 to 14 and columns 1 to 14, in column-major order: column 1 from the bottom up, then column 2, and so on.

K6 keeps the deepest prefix that it finds. The open cells collect in the top-right corner (Figure 4). On row 14, a piece must show a top colour that a free top-border piece can still match.

6.9End dives and polish

K7 End-dive engineFig 3 completes each stop-row board to 256 pieces. It accepts breaks. It writes the best result. Figure 6 shows its components. One dive obeys these rules:

  • It fills the open cell with the fewest exact fits first.
  • It places an exact fit when one exists.
  • When all open cells are stuck, it places a piece from the smallest break class.
  • It never goes back. It cannot fail, because the piece-type counts always balance.
  • Placed cells do not move.

For each configuration, K7 runs three stages:

  1. E2 Stage 1 divesFig 6: M/10 dives for each board. M is --end_dive.
  2. E3 Stage 2 learningFig 6: promising boards get the other dives in 18 cross-entropy rounds. After each round, the top 5 % of the dives vote. The votes change a weight w(piece, cell): w += 0.3 log((votes + ½) / (expected + ½)), clipped to ±2.
  3. Polish (--end_polish R): E4 Polish: climbFig 6 turns one piece or swaps two while a junction is gained. Then E5 Polish: walksFig 6 runs up to 16 walks that share R rounds of annealed swaps, with the temperature from 3 to 0.3.

Measured on 35 row-10 boards, 4 threads:

NOTE

E6 Keyed random streamsFig 6 gives each dive a random stream with a key from its board and its index. E1 Job queueFig 6 merges the results with order-independent keys. Thus the output does not depend on the thread count.

7Re-growth tools

7.1Finalizer

B2 FinalizerFig 2 reads partial boards. It locks each piece at or below row --finalize_from (default 5). The other pieces go back to the pool.

B2 builds the chain database again without the locked pieces. This database is much smaller. At --finalize_from 10, it has 5.5 million chains and takes about 2 s to build.

B2 then grows the rows above with the scoring, selection, parity test, exact search and dives of the beamer. Use --finalize_repeats N to run it again on the same board. The random band (--frac_rand, default 0.30 in B2) makes each repeat different.

7.2Roundhouse

A row-by-row search has a frontier of 16 colours. That frontier is too wide for an exact search. B3 RoundhouseFig 2 turns the board so that a strip of W columns lies against the right border. It fills the strip level by level. Each level is one chain of W − 1 inner pieces and a right edge piece. The frontier is then only W colours wide.

B3 builds a database of all such chains. At W = 5, it has 228.7 million records (0.51 GB). An oracle does one backward sweep over the strip and ignores piece reuse. It marks the frontier states that can still finish the strip. A branch with a dead state stops at once.

The search is exact and deterministic. An exhausted search proves that no break-free refill exists for that core and that pool. B3 then reports status=COLOR_DEAD. --rounds sets how many bands B3 frees and refills: the right band, then the top band, then the left band.

7.3The whirlpool

Stage B only grows upward. Thus it never changes the rows below. pipeline/run_pipeline_whirlpool.sh solves this problem. One lap has three steps:

  1. tools/E555_rotate.py turns the board a quarter-turn. The complete rows become columns.
  2. C3 BacktrackerFig 2 with --stop_row 5 --with_frame fills rows 0–5 and the 60 border cells with no break.
  3. B2 FinalizerFig 2 with --finalize_from 5 grows the board again to row T.

Four laps make a full turn. After a full turn, no piece stays in its cell.

8Stage C: closing

Stage C works on few boards and uses much time on each. Figure 7 shows the normal order of the calls.

8.1Distiller

C1 DistillerFig 2 reads plain or gzip CSV files of partial or complete boards. It keeps N boards (--top, default 25). P is the number of unique partial boards.

C1 writes the N boards and FILE.plan.sh. The plan holds the ender command for these boards. C1 calls C2 DiverFig 2 with a seed and a key for each board. Thus the output does not depend on the thread count or on interruptions.

8.2Diver

C2 DiverFig 2 runs K7 End-dive engineFig 3 on any board file. It needs no chain database. --holes lifts cells and makes a partial board. --pin_clue places clues. --stop_row first builds the top again with the rules of K5 Exact row searchFig 3 and K6 Column-major extensionFig 3.

8.3Backtracker

C3 BacktrackerFig 2 is a depth-first search with forward checking. A bitset index gives the exact-fit count of each empty cell.

  • --break_mode stuck (default) runs greedy dives. It proves nothing.
  • --break_mode any runs an exhaustive search with iterative deepening over the break count k. An exhausted level k proves that no completion with k breaks or fewer exists.
  • --stop_row N writes each filling of rows 0–N. B2 uses these files as input.
CAUTION

The search order of C3 is part of a file format. A --resume identifier records a path through the search. If you change the cell order or the candidate order, increase the version of the identifier format (bt1).

8.4Ender

C4 EnderFig 2 solves regions of a complete board exactly. Inside a region, pieces can change cell within their type and can change spin. The rest of the board stays fixed. C4 never returns a worse board.

The model uses the Boolean encoding of Heule (2008) in X2 OR-Tools CP-SATFig 1. C4 gives the current board as the hint. It keeps the break count at or below the current value.

A profile sets the plan. The plan starts with the cheapest step: swap (linear assignment), redive (C2 --reopen), windows of h × w cells, corner blocks, bands, then the frame. After a gain, the plan starts again.

8.5Topper

C5 TopperFig 2 minimizes the breaks in a band of open cells with CP-SAT. Its objective has three ranked parts: first the total number of breaks, then the distance of each break to the nearest horizontal border, then its distance to the nearest corner.

9Determinism

Some parts of E555 write byte-identical output at any thread count. The tests compare 1 thread with 4 threads for these parts.

PartSame output at any thread count
K5 Exact row searchFig 3, K6 Column-major extensionFig 3, K7 End-dive engineFig 3, C2 DiverFig 2Yes
C3 BacktrackerFig 2Yes
A1 Edge annealerFig 2Yes. The parent process replays the restarts in order.
K3 Beam loopFig 3No. With --rng_seed, a run repeats only on the same build and the same thread count.
CAUTION

In the exact engines, do not make the partition of the work depend on the thread count.

10Procedures

10.1Build and test

  1. Go to the root of the repository.
    cd E555
  2. Build the five binaries.
    make ARCH=generic
  3. Install OR-Tools.
    pip install ortools
  4. Run the core checks.
    ARCH=generic bash tests/run_tests.sh
  5. Make sure that each check passes.
CAUTION

Use ARCH=generic in containers, in CI and on clusters with mixed CPUs. A binary built with -march=native stops with SIGILL on an older CPU.

NOTE

A check that needs OR-Tools shows SKIPPED and passes when OR-Tools is not installed. Do step 3 before you trust a pass of the ender, topper or diver checks.

10.2Run the recommended workflow

  1. Make 16 borders with A1 Edge annealerFig 2.
    python3 src/A_border/E555_edge_annealer.py data/seed_Edge5.txt \
    --restarts 16 --steps 500000 --out rotations.csv
  2. Grow and dive the boards with B1 BeamerFig 2.
    bin/E555_beamer data/seed_Edge5.txt rotations.csv --start_row 0 --num_rows 1 \
    --clue_center --beam_width 10000 --backtrack_row 6 --stop_row 11 \
    --top_bottoms 6 --top_columns 12 --tau_bottoms 0.1 --tau_columns 0.1 \
    --extend_nodes 0 --end_dive 10000 --end_polish 20000 --emit_score 452 \
    --prefix run1 --db_file chain_center.db --out_dir beam_0
  3. Select the 25 best boards with C1 DistillerFig 2.
    python3 tools/E555_distiller.py beam_0/*.csv --top 25 --out best.csv
  4. Close the selected boards with C4 EnderFig 2.
    python3 src/C_tail/E555_ender.py data/seed_Edge5.txt best.csv closed.csv --profile deep
  5. Show the best closed board with T1 viewerFig 2.
    python3 tools/E555_viewer.py closed.csv --seed_file data/seed_Edge5.txt
CAUTION

D2 Chain databaseFig 2 needs 6.4 GB of disk and approximately 8 GB of RAM.

NOTE

Read the database file once after a reboot: cat chain_center.db > /dev/null. A cold page cache makes the first configurations 5 to 10 times slower.

10.3Add a flag to a C tool

  1. Add the parser entry strcmp(argv[i], "--x").
  2. Add the flag to the usage text.
  3. Add the flag to print_cmd().
  4. Add the flag to the Options table of the tool in PROJECT_E555.md.
  5. Update each script in pipeline/, examples/ and tests/ that uses the flag.
  6. Run the core checks.
    ARCH=generic bash tests/run_tests.sh
  7. Run the checks of the tool that you changed.
    ARCH=generic bash tests/run_tests.sh finalizer
NOTE

The core check scripts_parse fails when a script passes an unknown flag, or when print_cmd() does not mention each flag that the parser accepts.
